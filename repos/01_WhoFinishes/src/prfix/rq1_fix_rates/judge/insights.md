### Direct fix vs Related touch
- **Q corrects a value/logic P just wrote → fix; Q adds a sibling of what P wrote → related.** Pair 4 changes P's `FormatHelper.formatGradeForDisplay(getEnteredGrade())` to raw `getEnteredGrade()` (repairs P's exact line). Pair 18 leaves P's deprecated features untouched and deprecates *another* feature (`AliasValidatorSelectionAlgorithm`) alongside them — same pattern, no defect → related.
- **Blame/content overlap alone doesn't make a fix — check whether the overlap is the *point* of Q.** Pair 24 deletes 55 lines P authored in a test file, yet is Unrelated: Q re-applies the same `../src/utils.js` import fix independently (module-system work), not repairing P's ESLint bump. High `Q-removes-on-P` counts still require that Q's *intent* target P's defect.
- **"Continue the same effort" wording signals related, not fix.** Pairs 18, 48, 50 read as "deprecate the next one", "sanitise the format", "add more docs/troubleshooting" — additive momentum, explicitly noted by annotators as "incremental."
- **A later PR reverting/replacing P's own new mechanism because it misbehaves is a Direct fix even when the description is vague.** Pair 17 ("Fix the settings modal") rewrites 36 of P's lines restructuring the Dialog P introduced; pair 8 rewrites P's just-added ref logic to stop an infinite loop.

### Direct fix vs Unrelated/mislabeled
- **The named-PR chain is decisive.** Pair 2 explicitly cites the position change P made and repairs the resulting positional-arg bug on lines P wrote; pair 44 names the merge commit that broke `server.ts` imports and fixes the exact import P introduced. Contrast pair 43, where P only *moved* a file (P's diff to the shared file is literally "(none)") and Q fixes pagination in code P never authored → Unrelated despite same file.
- **Same big/common file + different subsystem = Unrelated, regardless of "fix" type.** Pairs 11 & 12: both P and Q edit `PerfViewData.cs`, but Q only reorders/adds a `using` (2 substantive lines) for a totally separate parser feature; P's heap/GC edits are elsewhere. Pair 45: both touch one usecase file, but P did webhook DI and Q strips email branding — disjoint regions.
- **Coincidental generated/version-bump overlap is the classic false positive.** Pair 10 (`package.json` version + CHANGELOG), pair 16 (Q *deletes* the changeset P added as part of a "Version Packages" release bot), pair 8's `pyproject.toml` version line — the [doc/data file] flag plus "do not touch any line P introduced" reliably rules these out even when line counts look like edits.
- **Constraint/config files edited by many housekeeping PRs are near-always Unrelated.** Pairs 36 (pytest config vs databricks-agents pin), 39 (pyspark pin vs openai pin), 40 (two different VS Code settings) each edit adjacent lines in a shared config for independent reasons.

### Common traps
- **Provenance note overrides the commit message.** Pair 31's message claims a fix but the automated check reports Q's net change on `dev-server.ts` is comment/whitespace-only (the substantive line is an intermediate PR's) → Unrelated. When the note says "comment/whitespace-only" or "none of P's added lines," trust it over "fix:" prose.
- **Context-line matches ≠ P's code.** Pairs 18, 37, 39, 48 show `Q-removes-on-P=0` with a few "P-lines-in-Q-context" — Q edits *near* P's lines but never on them; that is Related or Unrelated, never Direct fix.
- **A revert of P is a Direct fix.** Pair 46 (Q deletes the `hello.txt`/`hellostack.txt` P added) counts as Direct fix — Q exists to undo P's change on P's exact lines, even though it's a doc/data file.
- **"Fixes #NNN" citing a *different* issue than P's area is noise.** Pairs 21, 24, 42, 45 all carry crisp bug reports and "Fixes #..." yet address problems P never introduced — verify the cited defect maps to P's diff region.
- **Devin/Copilot sibling PRs by the same author on the same feature look linked but often aren't.** Pairs 36/39/40/42 share author + agent + area but pursue independent maintenance tasks; same-author + same-day + `fix:` is weak evidence.
- **Huge shared-file diffs can be duplicate independent work.** Pair 24 & 49 both apply the *same* `createSvgStr`/import refactor from separate branches — large identical-looking overlap that is actually parallel, unrelated effort, not Q repairing P.
- **Doc-only or link-refresh edits to a file P feature-touched are Related at most.** Pair 3 (Q rewrites the support-videos i18n block; P added hotkey strings elsewhere in `en.json`) and pair 50 (both edit README) are same-file, disjoint-region additive edits.
